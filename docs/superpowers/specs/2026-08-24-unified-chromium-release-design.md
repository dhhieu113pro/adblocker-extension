# Unified Chromium Release Design

Date: 2026-08-24
Repository: `dhhieu113pro/adblocker-extension`
Status: Proposed

## Goal

Use one extension version, one Git tag, and one tested build artifact for all supported Chromium-family distribution channels.

A release such as `v1.0.12` should produce exactly one packaged extension containing manifest version `1.0.12`, then distribute that same package to:

- GitHub Releases for manual/developer Chromium installation.
- Microsoft Edge Add-ons for Microsoft Edge.
- Chrome Web Store for Google Chrome.
- Brave through the Chrome Web Store listing, with no Brave-specific build or publishing workflow.

## Current State

The repository currently stores version `1.0.11` in both `src/manifest.json` and `package.json`.

The current release workflow builds tags matching `v*` but explicitly excludes tags ending in `-edge`.

The Edge publishing workflow is separately triggered by `v*-edge`, repeats install/test/build work, packages `dist/`, uploads the package to Edge Add-ons, waits for validation, and submits it for certification.

This produces browser-specific release tags and duplicate builds for what is fundamentally the same Manifest V3 Chromium extension.

## Design Decision

Adopt one release identity:

```text
manifest/package version: 1.0.12
Git tag:                 v1.0.12
artifact:                ai-vision-ad-blocker-v1.0.12.zip
```

Do not create `-edge`, `-chrome`, `-brave`, or `-chromium` version suffixes.

Store-specific item IDs remain different, but they all receive the same extension version and package bytes.

## Release Architecture

A single `vX.Y.Z` tag triggers the unified release workflow.

```text
v1.0.12
   |
   v
validate version
   |
   v
install + tests + browser E2E
   |
   v
build dist/ once
   |
   v
package ai-vision-ad-blocker-v1.0.12.zip
   |
   +-------------------+---------------------+
   |                   |                     |
   v                   v                     v
GitHub Release     Edge Add-ons       Chrome Web Store
                                             |
                                             +--> Chrome
                                             +--> Brave

GitHub ZIP --> generic Chromium/manual installs
```

The package generated by the build job is uploaded as a GitHub Actions artifact. Downstream publishing jobs download that artifact rather than rebuilding the extension.

This guarantees that Edge, Chrome, Brave users, and manual Chromium users receive binaries generated from the same source revision and test run.

## Version Source and Validation

The release tag is the release identity. Before building, CI must verify:

1. `GITHUB_REF_NAME` matches `vX.Y.Z`.
2. `src/manifest.json.version` equals `X.Y.Z`.
3. `package.json.version` equals `X.Y.Z`.

If any value differs, the release stops before publishing.

The implementation may include a small helper command for bumping both project version files together, but the release workflow must still validate them independently so accidental mismatches cannot reach a store.

## Workflow Structure

### Unified release workflow

Refactor `.github/workflows/release.yml` into the release orchestrator for tags matching only `v*.*.*`.

Recommended jobs:

- `build`
  - checkout
  - setup Node.js
  - `npm ci`
  - version validation
  - unit tests with the current 100% coverage gate
  - production build
  - Playwright Chromium installed-extension E2E tests
  - package `dist/`
  - upload package artifact
  - optionally upload diagnostics/screenshots

- `github-release`
  - depends on `build`
  - downloads the exact package artifact
  - creates/updates the GitHub Release

- `edge-store`
  - depends on `build`
  - downloads the exact package artifact
  - uploads to the existing Microsoft Edge Add-ons product
  - waits for package validation
  - submits the draft for certification

- `chrome-store`
  - depends on `build`
  - downloads the exact package artifact
  - authenticates to Chrome Web Store API v2
  - uploads the package to the existing Chrome Web Store item
  - submits the item for review/publishing

Store publishing jobs should run independently after the build so a slower Edge certification submission does not block Chrome submission, and vice versa. The overall workflow should still report failure if any configured publishing job fails.

### Existing Edge workflow

The standalone `v*-edge` trigger should be removed. Its current upload/validation/submission logic should either be moved into the unified release workflow or converted into a reusable `workflow_call` implementation invoked by the release orchestrator.

The preferred implementation is to keep store-specific logic isolated while making `release.yml` the only tag-triggered entry point.

## Chrome Web Store API

Use Chrome Web Store API v2, not v1.

API v2 supports service accounts and provides the upload and publish endpoints needed by GitHub Actions. Chrome Web Store API v1 is deprecated and is only supported until October 15, 2026.

One-time setup is required in the Chrome Web Store Developer Dashboard because API v2 does not create new store items. The extension listing and required metadata/privacy information must exist before CI can upload updates.

Recommended GitHub Actions secrets/variables:

- `CHROME_SERVICE_ACCOUNT_JSON` — service account credentials authorized for the Chrome Web Store publisher.
- `CHROME_PUBLISHER_ID` — Chrome Web Store publisher ID.
- `CHROME_EXTENSION_ID` — Chrome Web Store item/extension ID.

Do not create a Brave-specific credential or publishing integration. Brave installs compatible extensions from the Chrome Web Store.

## Existing Edge Credentials

Keep the existing Edge credentials:

- `EDGE_CLIENT_ID`
- `EDGE_API_KEY`
- `EDGE_PRODUCT_ID`

The unified workflow changes when these credentials are used, not how the Edge API itself works.

## Browser Targets

### Microsoft Edge

Distribution: Microsoft Edge Add-ons.

The package version must match the unified release version.

### Google Chrome

Distribution: Chrome Web Store.

The package version must match the unified release version.

### Brave

Distribution: the same Chrome Web Store listing.

No separate package, manifest, version, tag, or publishing job is required.

### Generic Chromium

Distribution: GitHub Release ZIP and/or `dist/` for developer-mode installation.

No separate package or version is required.

## Testing Strategy

Preserve the existing unit-test coverage gate and installed-extension Playwright Chromium tests before packaging.

The release must not publish if tests or build fail.

Add release-focused tests/checks for:

- tag/version parsing
- manifest/package version mismatch
- artifact name/version correctness
- package contains `manifest.json` at ZIP root
- package manifest version matches the tag

Store API calls should be structured so authentication, upload, and publish failures provide readable GitHub Actions errors.

A browser-specific source fork is out of scope unless an actual compatibility issue is later found. Current design assumes one Manifest V3 Chromium package.

## Failure Handling

- Version mismatch: fail before build/publish.
- Unit/E2E/build failure: publish nowhere.
- GitHub Release failure: report failure without rebuilding.
- Edge upload or validation failure: fail the Edge job with response details.
- Chrome upload or publish failure: fail the Chrome job with response details.
- One store failure must not cause the other store to rebuild a different artifact.

A retry should reuse the same release version/package where the store permits it; if a store accepted the version already, the workflow should detect/report that state rather than silently creating a different build.

## Documentation Changes

Update `README.md` to describe the project as a Chromium extension rather than Chrome-only/Edge-only and document installation paths:

- Chrome Web Store — Chrome and Brave.
- Microsoft Edge Add-ons — Edge.
- GitHub Release/manual unpacked installation — Chromium/development.

Document the unified release command/convention:

```text
vX.Y.Z -> one tested package -> GitHub + Edge + Chrome
```

Remove documentation that suggests `vX.Y.Z-edge` is needed.

## Non-Goals

- Separate browser-specific codebases.
- Separate Brave Store publishing.
- Separate browser version numbers.
- Firefox support in this change.
- Safari support in this change.
- Automated creation of the initial Chrome Web Store listing.

## Success Criteria

The change is complete when:

1. Pushing one tag such as `v1.0.12` triggers the complete release pipeline.
2. `src/manifest.json`, `package.json`, and the Git tag are validated as the same version.
3. Tests and build run once before distribution.
4. One ZIP artifact is created once and reused by all publishing jobs.
5. The GitHub Release contains that ZIP.
6. The same ZIP is submitted to Microsoft Edge Add-ons.
7. The same ZIP is submitted to the Chrome Web Store with API v2.
8. Brave users can install from the Chrome Web Store listing without a Brave-specific build.
9. Generic Chromium users can use the GitHub Release/manual installation path.
10. `v*-edge` tags are no longer required.
